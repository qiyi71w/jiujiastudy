# 04 — 每日按随机时间交付可恢复的日报

**What to build:** 学习者通过私信设置基准时间和显示时区，服务每天延迟 0–15 分钟采集并发送日报；重启、部分失败和发送故障不会重复扫描或丢失待发变化。

**Blocked by:** 02 — 在刷新日报中可靠呈现提交状态与部分失败

**Status:** ready-for-agent

**Guardrails:**
- 每账号计划日有稳定身份、持久随机时刻，至少区分待执行、采集中、有效日报已形成、逐端待投/已投、形成前取消。完整或明确标注失败的日报形成并持久化时算已扫描；发送是否成功另记。
- 已扫描但仅投递失败只重投，不重采；形成日报前取消不算已扫描。手动刷新只有挂接计划目的并保存计划日报和投递记录后才完成该计划，普通手动请求不消耗定时记录。
- 重启沿用该计划日身份和随机时刻；计划日为基准时间所属本地日期，跨午夜延迟不改变归属。只补当前应补的当日日报，不追发多日历史；改时区/时间保留执行事实，不创造同日额外自动扫描。
- 已确认的夏令时规则：夏令时重复时刻用第一次、缺失时刻顺延到当天首个有效时刻。status 显示实际计划结果。
- 输出一次生成，按启用渠道逐端记录；已知成功端不重发，失败按平台约束有界重试，回执未知不能承诺 exactly-once。投递重试队列只保留当日待发项及必要变化，不删当前/上一成功快照、逐课新鲜度、执行记录或长期决定。

- [x] help/status 均有设置入口，可改时间和 IANA 时区；status 显示实际下次扫描及最近完整性，不触发采集。
- [x] 计划日报包含未来七天待交、逾期、新增改期、最近已提交、新课、无日期任务、链接、时间及失败范围，无待交仍发确认。
- [ ] 固定时钟验证延迟、午夜、夏令时规则、改时区/时间、重启与当日补发，不重复抽取或执行；中途取消、日报形成未投递、部分端已投递三种状态均有持久证据。
- [x] 与 refresh 重合复用采集，命令和计划各自交付；发送重试无 Canvas 请求，清理不丢未交付变化。
- [ ] 受控短计划下真实 Telegram 收到一份日报；极端时钟与故障使用固定时间和本地服务验证，不修改生产每日频率。

原生要求：Telegram 测试 Bot，调度极端情况用受控时钟。覆盖 V07/V11/V12/V16；05实现关闭取消，07实现第二端，09最终验证。
